Making the whc.ca site more responsive

Findings from four Haiku investigations (hosting rules, build timing, which sources a browser can fetch, GitHub Actions and FTP behaviour), each checked before being relied on. Saturday, Oct 10 2026.

Short version. The site is slow to update because the workflow runs once an hour, at the top of the hour. That's the minute GitHub says it delays scheduled runs most. The build and upload are already fast: about a minute of fetching, four seconds of compute, and only the three board pages (about 4 MB) change between runs. The two changes that make the biggest difference: run every 15 minutes at odd minutes, which is free because the repo is public, and have the page's refresh button also pull Kambi and Novig, two of the sharp books, live in the browser. With that, the fair chance and EV move between publishes too. Building on the host or adding a PHP proxy there is not allowed by WHC's policy.

Two back-to-back builds left 3,128 of 3,131 files byte-identical. Only the three board pages differed. I confirmed in its source that the FTP action (SamKirkland/ftp-deploy, HashDiff.ts) compares content hashes, so a normal run uploads the 3 pages plus whatever player files changed. Player files only change when new games land. The first upload sends all ~3,100 files (35 MB) once. After that, uploads are small.

WHC shared hosting rules (Acceptable Use Policy, whc.ca/legal/aup, checked directly)

  • §16: cron "must not be scheduled more often than once every 10 minutes", at most 5 cron jobs, never overlapping.
  • §8(a): any process from the web server, cron or shell may not run "longer than 60 consecutive seconds", open more than 64 files at once, or use more than 5 threads.
  • §6(a): resources may only be used "to serve data from your web sites".
  • §11 (all accounts): "Proxy servers" are strictly forbidden.
  • Servers are LiteSpeed on cPanel/CloudLinux, in Montreal, Toronto or Vancouver (you picked one at checkout). SSH comes with the Pro and Enterprise plans, not Go.

Recommendations, best first

  1. doRun every 15 minutes, at odd minutes. GitHub's docs name the top of every hour as its high-load time, when scheduled runs get delayed. The repo is public, so Actions minutes are free. A 2–3 minute run every 15 minutes is well within limits, and the existing concurrency: publish group queues runs instead of overlapping them. For example, every 15 minutes from late morning to the late games, plus the 5 AM run: 
    on:
  schedule:
    - cron: '7,22,37,52 0-3,15-23 * * *'   # every 15 min, 11:07 AM to 11:52 PM ET (EDT)
    - cron: '13 9 * * *'                    # 5:13 AM ET: last night's stats
    I don't think splitting it into a fast "lines" job and a slow "logs" job is worth it. That was suggested, but refreshing logs takes 2 seconds and the tests 2 more, so there's little to save.
  2. doLet the refresh button pull Kambi and Novig too. Both answer any website, and both are sharp books in the fair chance. Re-fetching them alongside Underdog would refresh the main lines and the fair chance and EV between publishes, at no cost to the host. It needs their parsers ported from Python to the page's JavaScript (about 150 lines). The other five books keep their publish-time prices.
  3. doFetch the books at the same time instead of one after another. Fetching all books for all leagues at once would cut a run's network time from about 60 s to about 15 s, bounded by Bovada's own pacing, which stays. Small change in site.build / __main__. It mostly helps once runs are every 15 minutes.
  4. checkMake sure the pages are served compressed. The boards shrink about 10x gzipped (2.0 MB → 201 KB). LiteSpeed usually compresses by default, but WHC doesn't say so. Check with: 
    curl -sI -H 'Accept-Encoding: gzip, br' https://YOUR-DOMAIN/nfl.html | grep -i content-encoding
    If that prints nothing, a short .htaccess with AddOutputFilterByType DEFLATE text/html application/javascript and a short Cache-Control for *.html fixes it. I didn't have the domain, so I couldn't test this.
  5. optionalUse an external trigger if GitHub's schedule still lags. A free scheduler (for example cron-job.org) can call GitHub's workflow_dispatch API on the minute. It needs a fine-grained token limited to this repo with Actions write permission, kept only in that scheduler. That gives a third party a token, so only do it if the delays are still a problem after #1.
  6. unknownWill the books answer GitHub's servers? Every fetch was tested from your Mac, a Canadian home connection. GitHub's runners are in US data centres. DraftKings, FanDuel and especially Mise-o-jeu (Québec) might refuse them or answer differently. The first real run's log will say: the build prints "fetch failed" per book and falls back to the cache. If Mise-o-jeu is refused, the fallback is to run the same publish from your Mac every 15 minutes (a launchd job doing the build plus the FTP upload).
  7. don'tBuild on the host, or put a PHP proxy there. A proxy for FanDuel, DraftKings and others would be the obvious way around the browser restrictions, but §11 forbids proxy servers outright. Building on the host breaks §8 (a run needs about 60 s of network plus Python, and the cap is 60 s), §16 (cron every 10 minutes at most) and §6.
  8. don'tSwitch to lftp mirror --only-newer. One report suggested it to skip unchanged files, but it compares modification times. Every Actions run starts from a fresh checkout and rebuilds every file, so all 3,100 files would look new and upload every time. The current action already skips unchanged files by hash.

How the reports held up

Hosting: the policy quotes were accurate. It missed the §11 ban on proxies, which decides the proxy question, and I added it from the policy page. Build timing: numbers consistent and reproducible; its suggestion to move the "generated" timestamp out of the pages doesn't matter, since those pages change with every line move anyway. Browser access: I re-checked Kambi and Novig myself (both send access-control-allow-origin: *). Its note that DraftKings no longer needs the home-page cookies is from one test and isn't worth acting on. GitHub Actions and FTP: the schedule facts are cited from GitHub's docs. It couldn't confirm how the FTP action diffs files; I checked the source (content hash). Its lftp --only-newer suggestion would be a regression here (see the last item).
